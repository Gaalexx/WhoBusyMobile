## Модель продукта и роли

Пользователь ведёт личные планы и состоит в пространствах. Пространство — группа с
общим календарём, участниками и собственными ролями. Доска накладывает планы выбранных
пространств и, по желанию, все собственные планы пользователя.

Две системы ролей независимы:

| Поле | Значения | Значение прав |
| --- | --- | --- |
| `UserRead.role` | `admin`, `user` | Глобальный `admin` управляет аккаунтами; доступа к чужим пространствам/планам не получает |
| `SpaceRead.my_role`, `MemberRead.role` | `admin`, `moderator`, `actor`, `visitor` | Права конкретного участника в конкретном пространстве |

| Действие в пространстве | admin | moderator | actor | visitor |
| --- | --- | --- | --- | --- |
| Читать общедоступные планы и интервалы `busy` | Да | Да | Да | Да |
| Читать детали личных планов с публикацией `actors` | Да | Да | Да | Нет |
| Создавать собственные планы в пространстве | Да | Да | Да | Да |
| Изменять/удалять чужие планы, созданные внутри пространства | Да | Да | Нет | Нет |
| Видеть/обновлять ключ, приглашать, читать ожидающие приглашения | Да | Да | Нет | Нет |
| Управлять участниками и ролями | Все роли | Кроме админов; нельзя назначить `admin` | Нет | Нет |
| Переименовывать/удалять пространство | Да | Нет | Нет | Нет |

Каждое пространство сохраняет хотя бы одного администратора. Нельзя понизить последнего
админа или выйти, пока не назначен другой; API отвечает 400. Права владельца плана
действуют независимо от его роли в пространстве. Для чужого плана UI использует серверное
`can_edit`, а не только `owner_id` или глобальную роль.

## Общие правила HTTP

Все пути в таблицах относительны базовому URL. Через nginx FunProject это `/api/`;
FastAPI публикует маршруты без этого префикса. JSON использует `snake_case`.
Защищённые бизнес-маршруты требуют `Authorization: Bearer <access_token>`.
Исключения: `auth/register` и `auth/login` публичны; `auth/refresh` и `auth/logout`
работают по refresh-cookie без Bearer. `auth/logout-all` требует действующий Bearer.
`GET health` публичен и возвращает `{"status":"ok"}`.

Для nginx-адреса `https://whobusy.ru/` базовый URL клиента —
`https://whobusy.ru/api/`, если развёртывание сохраняет маршрутизацию репозитория.
Прямой FastAPI использует путь `/auth/...`; cookie path при таком подключении также
должен соответствовать внешнему пути, см. настройки сессии ниже.

Успешные ответы: 200 по умолчанию, создание — 201, операции без тела — 204.
Ошибки FastAPI содержат `detail`: строку для бизнес-ошибки или массив элементов для
валидации. Основные статусы: 400 — нарушение бизнес-правила, 401 — нет действующей
сессии, 403 — недостаточно прав/отключённый аккаунт при входе, 404 — объект не существует
либо недоступен, 409 — конфликт логина/email/приглашения, 422 — неверный формат данных.

Backend не раскрывает существование чужих пространств, приглашений и недоступных планов:
в соответствующих случаях возвращает 404. Деактивированный пользователь с ранее выданным
JWT получает 401 на защищённых запросах. Восстановление пароля по email отсутствует.
Сессия состоит из короткого access JWT и обновляемого refresh-token; выход включает
серверный отзыв refresh-сессии и очистку локальных данных клиента.

## Авторизация и профиль

| Метод | Путь | Запрос → ответ |
| --- | --- | --- |
| POST | `auth/register` | `RegisterRequest` → `Token` и `Set-Cookie`, 201; открытая самостоятельная регистрация |
| POST | `auth/login` | `{login, password}` → `Token` и `Set-Cookie`; `login` принимает логин или email |
| POST | `auth/refresh` | Без тела и Bearer; cookie `refresh_token` → новый `Token` и новый `Set-Cookie` |
| POST | `auth/logout` | Без тела и Bearer; отзыв семьи из cookie и удаление cookie → 204, также без сессии |
| POST | `auth/logout-all` | Без тела; Bearer обязателен; отзыв всех refresh-сессий текущего пользователя и удаление cookie → 204 |
| GET | `auth/me` | → `UserRead` |
| PATCH | `auth/me` | `ProfileUpdate` → `UserRead` |

- `RegisterRequest`: обязательны `login`, `password`, `first_name`, `last_name`; `email` необязателен, допускает `null`. Новому аккаунту назначается глобальная роль `user`.
- `Token`: `access_token`, `token_type` (по умолчанию `bearer`), обязательный `expires_in` — срок access-token **в секундах**, по умолчанию `900`. Refresh-token отсутствует в JSON. После регистрации и входа клиент получает пользователя отдельным `GET auth/me` с полученным Bearer.
- `UserRead`: `id`, `login`, `email: string?`, `first_name`, `last_name`, `full_name`, `role`, `color`, `is_active`. `full_name` вычисляется как «Фамилия Имя» с удалением внешних пробелов. Хеш пароля не возвращается.
- `ProfileUpdate`: необязательные `first_name`, `last_name`, `email`, `color`, `password`, `current_password`. Собственный логин и глобальную роль менять этим маршрутом нельзя. Для смены пароля нужен корректный `current_password`, иначе 400. `email: null` очищает адрес; `null` у других полей оставляет значение без изменений.

Логин нормализуется `trim + lowercase`, допустимы 3–32 символа `[a-z0-9._-]`.
Email необязателен, проверяется как email и также нормализуется `trim + lowercase`.
Пустая строка email не заменяет `null`. Логин и ненулевой email уникальны без учёта
регистра; конфликт — 409. Вход выбирает поиск по email, если поле `login` содержит `@`.
Пароль не обрезается и не меняет регистр. Схемы создания/обновления требуют 4–128
символов; это именно ограничение Pydantic, а не обещание поддержки backend-хешером
любого пароля такой длины в байтах.

Имена очищаются от внешних пробелов, максимум 100 символов. При регистрации оба имени
непустые; при редактировании профиля/создании аккаунта администратором фамилия может
быть пустой. Неправильный логин/пароль при входе — 401, отключённый аккаунт — 403.

## Access, refresh-cookie и отзыв сессии

Access-token — подписанный JWT, по умолчанию HS256 на 15 минут. Claims: `sub` (ID
пользователя строкой), `exp`, `type="access"`; роли и активность сервер каждый раз
читает из БД. Старые семидневные JWT без `type="access"` после обновления отвергаются
с 401. Клиент использует `expires_in` или факт 401, а не фиксирует срок в своём коде.

Refresh-token — случайная opaque-строка (`secrets.token_urlsafe(32)`), не JWT. В БД
хранится только SHA-256-хеш и сведения о семье сессии (`family_id`), сроках, ротации
и отзыве. Login и register создают новую семью; `refresh` продолжает ту же.

Ответы login/register/refresh устанавливают cookie `refresh_token`:

| Свойство | Подтверждённое поведение |
| --- | --- |
| `HttpOnly` | Всегда; JavaScript страницы не получает refresh-token |
| `SameSite=Strict` | Всегда |
| `Path=/api/auth` | По умолчанию, соответствует внешнему nginx-префиксу |
| `Domain` | Не задаётся, cookie относится только к выдавшему хосту |
| `Max-Age` | `REFRESH_TOKEN_EXPIRE_DAYS * 86400`, по умолчанию 2 592 000 секунд (30 дней) |
| `Secure` | При `COOKIE_SECURE=auto` зависит от первого значения `X-Forwarded-Proto`, при отсутствии заголовка — от схемы запроса; HTTPS включает флаг |

`COOKIE_SECURE=true/false` принудительно задаёт флаг. Настройки backend:
`ACCESS_TOKEN_EXPIRE_MINUTES=15`, `REFRESH_TOKEN_EXPIRE_DAYS=30`,
`REFRESH_REUSE_GRACE_SECONDS=30`, `REFRESH_COOKIE_PATH=/api/auth`, `COOKIE_SECURE=auto`.
Первые две переменные и `COOKIE_SECURE` явно проброшены в штатном docker-compose;
для изменения grace/path в контейнере нужно также передать соответствующие настройки
в backend. При прямом доступе без `/api` нужен подходящий `REFRESH_COOKIE_PATH`
(например `/auth`): браузер или cookie jar не отправляет `/api/auth`-cookie на `/auth`.

Каждый успешный `POST auth/refresh` выдаёт новый access и новый refresh-token той же
семьи, заново отсчитывая 30 дней от момента выдачи нового refresh. Старый токен
помечается ротированным, но ещё принимается в течение 30 секунд от его **первой**
ротации: это grace для параллельных запросов/вкладок. При повторе внутри окна
выдаётся ещё один новый токен, окно старого не продлевается. Предъявление такого
старого токена после окна отзовёт всю семью, включая уже выданные ей новые refresh.

Отсутствующий, неизвестный, истёкший или отозванный refresh даёт 401. Неактивный или
удалённый пользователь также не может обновить сессию. При любой ошибке refresh
ответ содержит `Set-Cookie` удаления с теми же path/флагами, `Max-Age=0` и истекшим
сроком. Возможные `detail`: `No session`, `Session expired`, `Session revoked`,
`Account is disabled`.

| Операция | Какие refresh-сессии отзываются |
| --- | --- |
| `auth/logout` | Вся семья из переданной cookie; без известной cookie просто 204 с её удалением |
| `auth/logout-all` | Все семьи текущего Bearer-пользователя; текущая cookie также удаляется |
| Собственная смена пароля (`PATCH auth/me`) | Все семьи, кроме указанной текущей refresh-cookie; **без cookie отзываются все** |
| Сброс пароля через `PATCH users/{id}` | Все семьи изменяемого аккаунта |
| `is_active=false` через `PATCH users/{id}` | Все семьи изменяемого аккаунта |
| `DELETE users/{id}` | Refresh-записи аккаунта удаляются вместе с аккаунтом |

Отзыв refresh не является немедленным отзывом уже выданного access JWT: после выхода
или смены/сброса пароля он действителен до `exp` (по умолчанию до 15 минут).
Отключение или удаление аккаунта немедленно закрывает защищённые запросы, поскольку
`get_current_user` проверяет актуального пользователя в БД.

### Обработка в native-клиенте

Android получает access из JSON, refresh — из HTTP `Set-Cookie`. Формат
`{refresh_token: ...}` в запросе/ответе не предусмотрен. `HttpOnly` запрещает доступ
JavaScript браузера, но не обработку заголовков нативным HTTP-клиентом.

Для общего браузерного cookie jar действуют `Domain`/host, `Path`, `Secure`, срок и
удаляющие `Set-Cookie`, в том числе в ответе 401. Текущий Android использует более
узкую схему для данного backend: `AuthAPI` извлекает **значение** `refresh_token`
из `Set-Cookie`, а `RemoteSessionManager` хранит его вместе с точным API base URL.
Это явная передача scoped credential, а не универсальный RFC cookie jar: атрибуты
cookie не сохраняются и не применяются как правила браузера.

HTTPS обязателен, HTTP redirect отключён. Cookie-заголовок с refresh отправляется
только на `auth/refresh`, `auth/logout` и `PATCH auth/me` настроенного API; обычные
запросы пространств/планов получают только Bearer. На PATCH профиля access и refresh
берутся одной атомарной парой, чтобы смена пароля сохранила текущую семью. Вход и
регистрация не подставляют демоучётные данные в удалённом режиме. Изменение base URL
не позволяет использовать сохранённый refresh другого API.

`RemoteSessionManager` последовательно меняет сессию под mutex: обновляет access за
30 секунд до ожидаемого истечения либо после 401, объединяет одновременные 401
одним refresh и повторяет каждый защищённый запрос не более одного раза. Ротация,
дисковая запись нового refresh и публикация сессии защищены от отмены вызывающей
корутины; запись завершается до публикации нового access. Смена пользователя/выход
увеличивают generation, и успехи/ошибки старых запросов не подменяют новую сессию.
Повторная 401 после обновления или 401 самого refresh очищает сессию. Login/register/
refresh/logout не запускают рекурсивное автообновление.

Access и профиль остаются в памяти. Refresh сохраняется в DataStore только в
AES-256-GCM envelope; ключ хранится в Android Keystore, файл — в `noBackupFilesDir`.
После нового запуска приложение обменивает сохранённый refresh на новый access,
затем читает `auth/me`. До окончания восстановления навигация показывает загрузку;
при временной ошибке доступны повтор и переход к новому входу. Повреждённое
хранилище/недоступный ключ или недействующий refresh приводят к повторному входу,
а не к использованию неподтверждённого профиля.

Локальный logout сначала дожидается удаления сохранённого refresh и очищает память;
отзыв серверной семьи запускается в фоне и при отсутствии сети выполняется best effort.
Это не подтверждение серверного отзыва: процесс может завершиться до отправки или
получения ответа.

В профиле есть отдельная кнопка «Выйти на всех устройствах» с подтверждением.
После подтверждения `logout-all` вызывает серверный endpoint и очищает локальную
сессию только после его успеха. Пока запрос выполняется, повторное подтверждение,
отмена диалога, Back и переходы из профиля блокируются. При временной сетевой или
серверной ошибке показывается сообщение, текущая локальная сессия сохраняется;
ошибки недействующей авторизации по-прежнему обрабатываются общими правилами 401.

Остаётся обычное окно потери ответа при вращаемом токене: сервер уже выполнил refresh,
но процесс завершился до получения/дисковой фиксации нового значения. Если следующий
запуск предъявит старый токен после серверного grace (30 секунд по умолчанию), семья
будет отозвана и понадобится новый вход. Неканцеллируемая запись уменьшает окно отмены
корутины, но не устраняет аварийное завершение процесса или отказ диска. Текущий API
не предусматривает идемпотентного восстановления потерянного ответа ротации.

Веб-клиент исходного backend-репозитория FunProject держит access только в памяти, восстанавливает его через
refresh после перезагрузки страницы и синхронизирует выход вкладок через
`BroadcastChannel`. В Android обменом и хранением управляет описанный нативный слой.
В WhoBusy2 модели, REST-репозитории, ViewModel и интерфейс находятся в
`shared/src/commonMain/kotlin/com/project/whobusy/`; Android HTTP/Keystore/DataStore — в
`shared/src/androidMain/`, общий `di/CalendarModule.kt` получает `AppConfiguration` из Android-графа.
`webApp` запускает тот же интерфейс с `DemoAppGraph` и моками в памяти. Серверная
авторизация для него пока не подключена: native-схему ручного Cookie/Set-Cookie нельзя
использовать из JavaScript браузера. Нужен отдельный browser HTTP/auth-адаптер с
credentials, HttpOnly refresh-cookie и согласованными CORS, SameSite, Secure и Path.
Refresh не должен становиться доступен JavaScript или сохраняться в localStorage.

## Доска

| Метод | Путь | Запрос → ответ |
| --- | --- | --- |
| GET | `users/me/board` | → `BoardSettings` |
| PUT | `users/me/board` | `BoardSettings` → сохранённый `BoardSettings` |

`BoardSettings = {space_ids: int[], show_own: boolean}`; `space_ids` обязателен,
`show_own` по умолчанию `true`. Сервер сохраняет выбранные пространства и флаг между
устройствами, убирает повторяющиеся/недоступные ID. При чтении тоже исключает пространства,
членство в которых завершилось.

«Мои планы» — `space_ids=[]`, `show_own=true`. Пустая доска — `[]`, `false`.
Общая доска получается явным выбором ID всех текущих пространств; специального `all`
в запросе нет. Создание/вступление в пространство само по себе не добавляет его в
сохранённую доску: клиент должен обновить `BoardSettings`, если это нужно его сценарию.

| GET | `spaces/{id}/invitations` | → `InvitationRead[]`; `admin`/`moderator` |
| POST | `spaces/{id}/invitations` | `{login, role?}` → `InvitationRead`, 201; `admin`/`moderator`, роль по умолчанию `visitor` |
| DELETE | `spaces/{id}/invitations/{invitationId}` | → 204; `admin`/`moderator`; модератор не отзывает приглашение на роль `admin` |
| GET | `invitations` | → собственные входящие `InvitationRead[]` |
| POST | `invitations/{id}/accept` | Без тела → `SpaceRead`; только приглашённый, вступление с предложенной ролью |
| POST | `invitations/{id}/decline` | Без тела → 204; только приглашённый |

- `SpaceRead`: `id`, `name`, `my_role`, `member_count`, `invite_code: string?`. Ключ возвращается только `admin`/`moderator`, остальным `null`. Название: 1–100 символов после `trim`.
- `MemberRead`: `user_id`, `login`, `full_name`, `color`, `role`, `joined_at` (ISO datetime).
- `InvitationRead`: `id`, `space_id`, `space_name`, `user_id`, `login`, `full_name`, `role`, `invited_by_name: string?`, `created_at`.

Приглашение по логину **не добавляет** человека сразу. Оно доступно для существующего
активного аккаунта; несуществующий/отключённый логин — 404. Уже участник или уже
приглашён — 409. Принятие/отклонение удаляет ожидающее приглашение. Ключ позволяет
войти сразу как `visitor`; повторное присоединение не меняет текущую роль, а ожидающее
приглашение при новом вступлении по ключу удаляется. Ключ чувствителен к регистру,
обрезаются только внешние пробелы; сервер генерирует 12 URL-safe символов.

При выходе/исключении участник сохраняет свои планы: его планы внутри этого пространства
становятся личными, публикации его личных планов в это пространство удаляются.
Удаление пространства сохраняет планы всех участников как личные, удаляет его членства,
приглашения и публикации. Это отличается от удаления аккаунта, которое удаляет его планы.

## Планы: поля, видимость и изменение

| Метод | Путь | Контракт |
| --- | --- | --- |
| GET | `events` | → `EventRead[]`; query `start?`, `end?`, `space_ids?`, `own?` |
| POST | `events` | `EventCreate` → `EventRead`, 201 |
| PATCH | `events/{id}` | `EventUpdate` → `EventRead` |
| DELETE | `events/{id}` | → 204 |

Отдельного `GET events/{id}` нет: экран деталей использует событие из загруженного списка.
Параметр `space_ids` — ID через запятую; `space_ids=` явно выбирает ни одного
пространства, отсутствие параметра использует сохранённую доску. Недоступные ID
отбрасываются, нечисловые — 422. `own` — boolean, при отсутствии используется `show_own`.
`own=false` исключает добавление всех собственных планов отдельным источником, но
свои планы всё ещё попадают в выборку через выбранное пространство. План возвращается
один раз, даже если виден через несколько пространств; наиболее полная видимость
побеждает. Глобальный `admin` не обходит эти правила.

`EventBase`: обязательны `title`, `start`, `end`; остальные поля имеют значения по
умолчанию: `description=""`, `location=""`, `all_day=false`, `status="busy"`,
`color=null`, `rrule=null`. Статусы — `busy`, `free`, `tentative`.

`EventCreate` добавляет `space_id: int? = null` и `shares: EventShareItem[] = []`.
`EventShareItem = {space_id: int, visibility: "actors" | "busy"}`.
Указывать можно только собственные пространства. Повторяющийся ID в `shares`
сворачивается, последнее значение побеждает.

Четыре уровня публикации:

| Режим | Представление в запросе | Кто видит |
| --- | --- | --- |
| Создан внутри пространства | `space_id` установлен | Все участники этого пространства с полными деталями |
| Личный, только акторам и выше | `space_id=null`, share с `visibility="actors"` | `actor`/`moderator`/`admin` указанного пространства; `visitor` не получает план |
| Личный, только время занятости | `space_id=null`, share с `visibility="busy"` | Все участники получают маскированный план |
| Личный, не отправлен | Для пространства нет элемента в `shares` | Через это пространство план не виден |

У личного плана выбор независим для каждого пространства. Для созданного внутри
пространства плана непустой `shares` запрещён (400). Нельзя представить «виден всем»
для личного плана значением `visibility="public"`: такого enum в API нет.

`EventRead` содержит все поля `EventBase` и: `id`, `owner_id`, `owner_name`, `space_id`,
`shares`, `busy_only`, `can_edit`, `display_color`. `shares` заполнен только владельцу,
другим всегда `[]`. `display_color` — переопределение события либо цвет владельца.
При `busy_only=true` сервер возвращает `title="Занято"`, пустые `description`/`location`,
`color=null`, `can_edit=false`; имя/ID владельца, время, статус, `all_day`, `rrule`
остаются в DTO. Мок обязан маскировать данные до передачи в UI.

Владелец может изменять/удалять свои планы. Админ/модератор пространства может
изменять/удалять чужой план, **созданный внутри** этого пространства; публикация чужого
личного плана не даёт прав редактирования. Только владелец меняет `shares`.

`EventUpdate`: необязательные `title`, `description`, `location`, `start`, `end`,
`all_day`, `status`, `color`, `rrule`, `shares`. Отсутствующее поле сохраняется;
`shares=[]` убирает все публикации личного плана, `shares=null` их не меняет.
`color=null` и `rrule=null` очищают значения. У остальных обязательных полей
`EventBase` клиент не должен отправлять `null`. `space_id` отсутствует в update-схеме:
перенос плана между личным и пространством через PATCH не поддерживается.

Сервер отвергает `end < start` (400), но разрешает одинаковые начало/конец.
Непустой title и строго положительную длительность клиент может проверять как
собственное UX-правило; это не backend-валидация.

Время — ISO datetime, «плавающее» локальное время без пересчёта часовых поясов.
`start` и `end` query необязательны. Неповторяющиеся планы фильтруются по пересечению
с включёнными границами (`event.end >= start`, `event.start <= end`). Серии с
`rrule != null` возвращаются независимо от диапазона; повторения разворачивает клиент.
Backend хранит RRULE как строку, не разворачивает и не проверяет её синтаксис.
Изменение/удаление — всей серии, отдельных вхождений/исключений нет.

## Аккаунты: только глобальный администратор

| Метод | Путь | Запрос → ответ |
| --- | --- | --- |
| GET | `users` | → `UserRead[]`, сортировка по фамилии/имени |
| POST | `users` | `UserCreate` → `UserRead`, 201 |
| PATCH | `users/{id}` | `UserUpdate` → `UserRead` |
| DELETE | `users/{id}` | → 204; себя удалить нельзя (400) |

`UserCreate`: обязательны `login`, `password`, `first_name`; `last_name=""`,
`email=null`, `role="user"`, `color="#4c5c9e"`. `UserUpdate` принимает необязательные
`login`, `first_name`, `last_name`, `email`, `role`, `color`, `is_active`, `password`.
`email:null` очищает email, `null` у остальных полей оставляет прежнее значение.
Сброс пароля администратором не требует `current_password` и отзывает все refresh-сессии
аккаунта. Блокировка `is_active=false` также отзывает их; сервер проверяет активность
при каждом защищённом запросе.

Удаление аккаунта удаляет его планы, входящие приглашения и refresh-записи. Если он был последним
админом пространства, сервер назначает преемника (наиболее ранний участник, с
предпочтением модератора); пространство без участников удаляется. Endpoint не
предоставляет просмотр чужих планов глобальному администратору.

## Android: моки и подключение

По умолчанию Android-приложение использует REST. `-PwhoBusy.useMockData=true`
включает моковый источник без сетевых запросов. Данные сессии,
изменения планов, пространства, приглашения и настройки доски в демонстрационном
режиме хранятся в памяти и сбрасываются вместе с процессом; серверное сохранение
`BoardSettings` описывает реальный backend, а не постоянное хранилище моков.

В общем коде `shared/src/commonMain` на едином наборе моков реализованы регистрация и вход по логину/email,
доска по пространствам, отдельные роли и права, вход по ключу, подтверждение приглашений,
личные и пространственные планы с маскированной занятостью, профиль и администрирование аккаунтов.
Разворачивание повторений выполняется на клиенте; исходные даты серии сохраняются
при редактировании выбранного вхождения.
Функции, отсутствующие в REST API (например восстановление пароля, отдельные вхождения
серии, произвольный перенос плана в другое пространство), нельзя представлять как
поддерживаемые backend-возможности.

В коде реализованы три согласованные удалённые реализации:
`RemoteAuthRepository` (регистрация/вход/восстановление/выход/выход со всех устройств),
`RemoteWorkspaceRepository` (пространства, доска, участники, приглашения, профиль,
аккаунты) и `RemoteCalendarRepository` (планы и CRUD). Общий `AuthenticatedHttpClient`
использует `RemoteSessionManager`; legacy-методы выбора ownerIds не вызывают удалённые
маршруты и возвращают ошибку неподдерживаемой операции.

В Android-графе `USE_MOCK_DATA` по умолчанию `false`: Auth/Workspace/Calendar используют remote. Web использует только `DemoAppGraph` с моками; Android-свойства не включают REST в браузере.
`-PwhoBusy.useMockData=true` переключает сразу все три репозитория на моки.
`-PwhoBusy.useMockData=false` явно выбирает REST, без смешивания с моковыми пространствами. Базовый
URL по умолчанию — `https://whobusy.ru/api/`; для своего сервера его можно переопределить:

```bash
./gradlew :androidApp:assembleDebug -PwhoBusy.useMockData=false
# Необязательное переопределение адреса:
./gradlew :androidApp:assembleDebug -PwhoBusy.useMockData=false \
  -PwhoBusy.apiBaseUrl=https://<server>/api/
```

Android-конфигурация принимает HTTPS без credentials/query/fragment. JWT, refresh и
пароли не передаются через Gradle. Моки не используют сохранённую серверную сессию;
в моковой сборке приложение не обращается к API даже при заданном base URL.

Описание выше отражает реализацию исходников; факт сборки, запуска тестов и проверки
живого сервера отмечается отдельно в [AGENT_MAP.md](AGENT_MAP.md). Наличие remote-кода
и параметра сборки само по себе не подтверждает успешную операцию на сервере.

Моки воспроизводят основные права и побочные эффекты API, но не заменяют его серверную
валидацию. Форма требует положительный интервал (сервер допускает равные границы);
мок защищает последнего активного глобального администратора и отклоняет повторные
shares одного пространства, тогда как backend при повторении берёт последнее значение.

Границы интерфейса и источник макета: [DESIGN_REFERENCE.md](DESIGN_REFERENCE.md).
Фактические точки входа, репозитории и проверки Android: [AGENT_MAP.md](AGENT_MAP.md).
